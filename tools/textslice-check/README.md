# tools/textslice-check —— 大文本切片 / 拼接的断言

「文本查看器能不能编辑」这个问题在 3.14.0 之前一直是**按文件体积判**的：
文件超过 `MAX_FULL_BYTES`（4MB）就只读前 512KB，并且把编辑入口一并禁掉。
结果是一个 7.8MB 的文本**一个字节都改不了** —— 而它其实只需要
「让控件一次少拿一点字符」就行。

现在改成按**字符数**切片（`TextSlicer`），浏览与编辑都只把**当前一片**交给控件，
保存时逐片拼接。这个目录就是这套东西的断言。

## 为什么必须有离线断言

`TextSlicer` 干的活是「字节与字符的换算」+「按片拼接写回」，而这两件事
**错一点都不会当场报错**：

- 切点落在多字节字符中间 → 那一处变成替换字符；
- 片与片之间漏一个字节 → 内容少了一点，文件照样打得开；
- 拼接时把没改过的片重新编码 → 编码探测一猜错就是整篇乱码。

要在真机上发现这些，得先有那份「特定的、边界的」文件。所以判据全部下沉到
**逐字节级别**，并且一条命令就能跑（纯 Java，零 Android 依赖）。

## 跑法

```sh
# ① 行为断言：切片 / 拼接的真实字节（143 项）
JAVA_HOME="C:/Program Files/Java/jdk-20" sh tools/textslice-check/run.sh

# ② 源码不变量：判据有没有改一半、有没有留下旧路径（94 项）
python3 tools/textslice-check/verify-textslice.py
```

## 断言表

| 文件 | 内容 |
| --- | --- |
| `run.sh` + `TextSliceCheck.java` | **行为断言，143 项**。十节：字节形态判定 / 片边界落在行首（UTF-8、GBK、UTF-16LE、UTF-16BE、ISO-8859-1 五种编码）/ 切片无损（所有片拼起来 == 整篇解码）/ BOM 识别与保留 / 拼接写回（没改的片**逐字节**原样）/ 行数核对 / 超长行硬切 / 边界输入 / **最长行** / **片大小上限** |
| `verify-textslice.py` | **源码不变量，94 项**。十二节，见下 |

`verify-textslice.py` 的十二节：

| 节 | 钉住的东西 |
| --- | --- |
| 1 | `TextSlicer` 必须保持纯 Java（不然离线断言跑不了） |
| 2 | **BOM 判据与 `TextCodec` 逐条一致** —— 这个判据现在有两处定义，最怕改一边 |
| 3 | 解码策略两边一致（`REPLACE`：坏字节变 U+FFFD，不抛异常） |
| 4 | 不再有「文件大就禁编辑」这套错判据（`MAX_FULL_BYTES` / `truncated` / `DISPLAY_LIMIT_*` 都不许再出现） |
| 5 | 保存是「拼接 → 行数核对 → 备份 → 覆盖」，**顺序不许乱** |
| 6 | 跨片的改动一个都不能丢（`confirmExit` 必须按 `editedSlices` 判，不能按编辑框脏没脏） |
| 7 | 片导航：布局里有、代码里用、单片文件时看不见 |
| 8 | 分片之后几处「视野内」语义跟着改（查找报全文行号、复制改称本片、跳行不悄悄夹底） |
| 9 | `TextCodec.SUPPORTED` 里每一种编码都在行为断言里出现过 |
| 10 | 本目录自身的完整性 |
| 11 | **`SLICE_CHARS` 的取值区间** + `LONG_LINE_WRAP` + `SliceBench` 里抄的那份常量必须与查看器一致 |
| 12 | 编辑模式的峰值内存与兜底（先放掉浏览侧 / `try/catch` / 失败时说人话） |

## 三个必须记住的判据

**① 按字符数切，不按字节数。** 控件的开销看的是字符数；UTF-8 下一个汉字
3 字节却只有 1 个字符，按字节切会让中文片只有纯 ASCII 片的 1/3。

**② 保存时「没碰过的片」按原始字节复制，不重新编码。** 这一条是
「编码探测猜错也不会把文件写坏」的唯一保证。只有用户真的改过的那一片
才用编辑后的文本重新编码。

**③ 片大小是唯一一个数量级杠杆。** 一次塞给控件的字符数直接决定
`StaticLayout` / `DynamicLayout` 的构建时间与每翻一页的临时分配，而这个量
**跟文件多大无关**。3.14.0 取 200 万（理由是"与旧的上限对齐"，但那个上限
在旧版里因为有 4MB 截断而**从未被真机走到过**），真机上的表现是：
加载要等、滑不动、ANR、点编辑闪退。现在是 10 万 —— 一屏 2000~5000 字符，
10 万是 20~50 屏，正常阅读几乎碰不到片边界。**改这个数之前先跑
`tools/perf-check`**，那里有不同片大小下的耗时与分配对照。

## 片边界之外：显示侧的折行

片大小调小之后还有一个坑：**一整行十万字符**（压缩过的 JSON、base64、单行日志）。
不折行渲染时控件宽度由最长行决定，会撑出几十万像素宽、滚动直接废掉。
所以 `TextSlicer.longestLine()` 量出本片最长行，超过 `LONG_LINE_WRAP`（500）
就**强制折行**（按钮文案变成「换行: 自动」）。它只影响显示：`\n` 的个数没变，
行号、查找、写回都不受影响。

## 夹具为什么是"文本内容随机、片上限故意调小"

`TextSliceCheck` 里所有多片用例都把 `maxChars` 设成 40~500 ——
这样**几 KB 的夹具就能切出几十片**，覆盖到所有边界，跑起来也只要一两秒。
真按线上那个上限去造夹具，得先写一个几 MB 的文件，慢且没必要。

夹具全部建在系统临时目录，跑完即删。
