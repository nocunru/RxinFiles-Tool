# perf-check —— 文本查看器「读取 / 修改」链路的性能基准

不是断言，是**量尺**。存在的唯一理由：有人提「优化文本读取 / 换 native / 上 mmap」时，
先量一遍，别对着只占几毫秒的环节下功夫。

```sh
JAVA_HOME="C:/Program Files/Java/jdk-20" sh tools/perf-check/run.sh
```

夹具写在 `${TMPDIR:-/tmp}/rxin-perf`，不落进工程。

## 两个限制（先读再信）

1. **JVM 的数字，不是 ART 的。** 手机上绝对值大几倍（尤其 `RandomAccessFile`
   的系统调用与 `mmap` 的缺页）。能用的是**各步骤之间的比例**和**候选写法之间的
   相对速度**，不能把毫秒数当成手机上的指标。
2. **量不到 UI。** 真正的开销在 `setText` → `StaticLayout.generate()`（逐行排完全部文本，
   不懒加载）与编辑模式下 `DynamicLayout` 的整篇 reflow —— 都是 framework 代码，
   脱离设备跑不了。本基准只能说明**「IO 与字节处理这一侧还剩多少水」**。

## 两支

| 脚本 | 量什么 |
| --- | --- |
| `SliceBench.java` | **3.14.0 起的切片链路**。直接调**真的** `TextSlicer`（不是等价实现），外加「候选扫描写法对比」 |
| `PerfRead.java` | 3.14.0 **已被删掉**的旧读取链路，留作「旧的那 10ms」的对照 |

`SliceBench` 的夹具：`zh-7_8m.txt`（7.8MB UTF-8 中文）、`zh-50m.txt`（50MB 同款）、
`oneline-1m.txt`（1MB 单行，专治「一整个大行」）。

## 当前结论（3.14.2 实测）

### 1. 打开 7.8MB：全文扫描只占 12 ms 量级，不是瓶颈

```
scan（含逐字符统计）   7.8MB   11.96 ms      50MB   71.01 ms      1MB 单行  4.09 ms
```

`scan` 是 O(文件) 且**在打开时必经**，50MB 以上才开始变成可感知的等待。

### 2. 「用 mmap 更快」是对的 —— 但 Java 本来就有 mmap

只数换行（7.8MB / 50MB）：

| 写法 | 7.8MB | 50MB |
| --- | --- | --- |
| A `RandomAccessFile` + 1MB 缓冲 + 逐字节（**现状**） | 5.12 ms | 28.10 ms |
| B `FileInputStream` + 1MB 缓冲 + 逐字节 | 4.98 ms | 28.52 ms |
| C `FileInputStream` + word trick | 4.58 ms | 25.75 ms |
| **D `mmap` + 逐字节 `get()`** | **2.69 ms** | **17.04 ms** |
| E `mmap` + 整块拷进 `byte[]` + 逐字节 | 3.72 ms | 22.12 ms |
| F `mmap` + 整块拷 + word trick | 3.29 ms | 19.20 ms |

`mmap` 确实快约 **2~3 倍**（省掉了「读进 byte[]」那次拷贝）。
**但 `FileChannel.map()` 就是 mmap**，用不着换语言。

注意 D 比 E、F 快：逐字节 `get()` 走的是 intrinsic，**比"整块拷进 byte[] 再扫"更快** ——
和「mmap 要先拷出来才快」的直觉相反。别照直觉改。

### 3. word trick 在 CJK 上**更慢** —— 纯 Java 逐字节已接近上限

UTF-8 字符数统计（非续接字节计数）：

| 写法 | 7.8MB | 50MB |
| --- | --- | --- |
| 逐字节（现在是这么写的） | **3.74 ms** | **24.48 ms** |
| 8 字节 word trick | 5.20 ms | 36.95 ms |

中文文本里续接字节占比极高，8 字节快路径几乎从不命中，白搭一层开销。
**含义：想在字节处理上再快一个数量级，只能上 NEON SIMD 写 native；
而这条路的绝对收益就是把 12 ms 变成几毫秒。**

### 4. 真正的大头：解码写法（改一行快 3 倍）

| 写法 | 耗时 |
| --- | --- |
| A 现状 `TextSlicer.decode`（**每次新建 `CharsetDecoder`**） | **12.19 ms** |
| B 缓存 `CharsetDecoder` 实例 | 4.13 ms |
| C `new String(bytes, charset)` | **4.02 ms** |
| D `new String(bytes, UTF_8)` | 4.03 ms |

三者结果**逐字符相同**（长度 1999984），坏字节输入的 REPLACE 语义也一致（`a?b?c`）。
`String(byte[], Charset)` 内部走的是 `StringCoding` 的优化路径，语义就是
`onMalformedInput(REPLACE)` + `onUnmappableCharacter(REPLACE)`。

### 5. 最大的那个数：一片多大，决定每次翻页分配多少垃圾

7.8MB 文件：

| 片字符上限 | 切片数 | `readSlice` | **每次分配** | 首片字符 |
| --- | --- | --- | --- | --- |
| 2,000,000（**3.14.0，真机否决**） | 3 | 23.31 ms | **16.55 MB** | 1,999,984 |
| 500,000 | 9 | 9.78 ms | 4.14 MB | 499,968 |
| 200,000 | 21 | 2.05 ms | 1.66 MB | 199,976 |
| **100,000（3.14.2 现状）** | **42** | **0.47 ms** | **0.83 MB** | 99,960 |
| 20,000 | 207 | 0.22 ms | 0.17 MB | 19,992 |

**每翻一片分配 16.55 MB**（3.78MB 字节数组 + 4M `char` + 解码中间体），
之后还要 `setText` 让 `StaticLayout` 排 200 万字符；进编辑模式则是
`DynamicLayout` 对 200 万字符整篇 reflow。

> `readSlice` 那一列**波动很大**（JIT 预热与 GC 时机，同一份夹具两次能差 4 倍）。
> **稳定可比的是「每次分配」** —— 而它恰好就是决定 GC 压力的那个数。
> 所以调片大小要看分配量，不要看那一列时间。

片降到 1/20，这两样同时降到 1/20 —— **这是整条链路唯一的一个数量级杠杆**，
而它跟用什么语言写 IO 完全无关。

### 6. 保存：

```
merge：逐片拼接（无改动，7.8MB）        4.84 ms
countLines：写回前的行数核对（重扫新文件）  12.15 ms
```

`countLines` 为了一次核对**把新文件整个再扫一遍**；可以和 `merge` 合到同一次遍历里。

## 结论

**已经做了的（3.14.2）**：`SLICE_CHARS` 从 200 万降到 10 万。

真机反馈坐实了第 5 节那行数：7.8MB 中文文本，3.14.0 的表现是
**加载要等 / 滑不动 / ANR / 点编辑闪退**。现在每片 10 万字符、0.83MB。

**还剩两处可做**：

1. `decode` 换写法（12.19 → 4.02 ms，**3 倍**，语义已验证等价）
2. 打开时懒切片（把 O(文件) 从必经路径上摘掉）+ `countLines` 并入 `merge`

**换 native + mmap 能拿到的**：把第 1 节那 12 ms 压到几毫秒。**换不到**的是第 5 节 ——
`StaticLayout` / `DynamicLayout` 是 framework 代码，换语言一行都碰不到。
**这是本目录存在的意义：先看第 5 节的数，再决定要不要为第 1 节写 C。**

## 一条方法论上的教训（3.14.2 补记）

3.14.0 把 `SLICE_CHARS` 定成 200 万，理由写的是「与旧实现的 `DISPLAY_LIMIT_NORMAL`
对齐，每一片都不会比原来一次显示的那一大坨更吃力」。

**但那个"原来"从来没有发生过**：旧实现有 `MAX_FULL_BYTES = 4MB`，文件一大就只读
前 512KB 并禁用编辑 —— "一次显示 200 万字符"这条路径**在旧版里走不到**。
于是真机第一次真正走到它时，四条症状一起出现。

**"不更差"不能只算数，还得先确认那个"原来"真的发生过。**
拿一个没被验证过的理论值当底线，等于用一个不存在的基线给自己发通行证 ——
这跟本目录里已经记过的「JVM 数字不是 ART 的」是同一类错。
