# code-check —— 工程级静态自检

`tools/` 下其它套件都是**按功能**组织的（归档、查找、图片、外部打开、脚本、排序、切片、UI），
各自盯自己的判据。这一份管的是**不属于任何功能、属于工程整体**的那一类问题。

来源：3.15.10 那次「全方位查 bug」。人工扫了一遍之后，把其中**能精确判定**的固化下来。

用法：

```sh
python3 tools/code-check/check-code.py          # 在工程根目录或任意目录都行
```

## 三条断言（会判失败）

| 断言 | 判据 | 为什么 |
| --- | --- | --- |
| 无悬空资源引用 | 布局 / 代码里 `@drawable` `@color` `@string` `@style` `@layout` 的名字必须真的被定义 | 编译期能抓大部分，但判据放在这里是**为了跨机器一致**：换台机器、改了目录结构，编译不一定跑，脚本会跑 |
| 无共享的有状态格式化器 | 类 / object 的**直接成员**（4 空格缩进）不许是 `SimpleDateFormat` / `DateFormat` | 它们内部有可变 `Calendar`；调用点在 `Dispatchers.IO` 上，协程取消是**协作式**的（这条链路上没有挂起点，不会立刻停）→ 两个线程共用同一实例 → **解析结果错乱而不是抛异常**，`try/catch` 兜不住。3.15.10 实测发现 `ls -la` 的时间列可能串成别的文件的时间 |
| 无孤儿断言 | 有 `main` 的 `*Check.java` 必须真的被 `.sh` 执行 | `TarCheck` / `SelectCheck`（archive-check）与 `FindCheck`（find-check）写完就**没进任何 run 脚本**，从来没被执行过。「断言要能真的失败才算数」—— 一个不跑的断言连失败都做不到 |

### 第三条踩过的三个坑（值得记住）

写成「在一个大文本里找名字」的判据时，**注释一定会污染它**：

1. 一开始连 `.py` 一起扫 → **脚本自己的注释**里提到的类名成了「在跑」的证据，永远绿。
2. 改成只扫 `.sh` → 还是绿：`SelectCheck` 仍以 **`xxx.java` 编译路径**的形式出现。
   **被编译进去 ≠ 被执行**。
3. 剥掉 `.java` 路径引用 → 还是绿：`run-checks.sh` 里**新加的那段说明注释**又写了它。
4. 再加「剥掉整行 shell 注释」→ 终于精确红 1 条。

**每一步都是变异测试逮出来的**（把 `SelectCheck` 从清单里摘掉，看断言会不会红）。
所以：写这类判据要**先剥注释**，剥完必须用变异测试确认它真的会红。

## 两节只报告、不判失败

脚本最后会列出：

* **定义了但没人引用的资源** —— 改名、删功能之后最容易剩下的东西
* **布局定义了却没被代码引用的 id** —— 可能是漏绑定，也可能纯装饰，看一眼睛才知道

它们**只列出来给人看，不计入成败**。原因：机器判不准。比如 `Theme.RouXin.Base` 是被
`parent="..."` 继承的（真实的「被引用」），`ic_check` 可能只是留着备用。
**误报一次，这个脚本就没人再看了** —— 宁可只报告。

## 已知的假阴性（接受）

* `companion object` 里的 `SimpleDateFormat` 字段（缩进 8 空格）不会被抓到。
  收紧到 4 空格是为了**绝不误报函数体内局部变量**（那是安全的常见写法）。
* 判「悬空资源」时忽略 `parent="..."`（`Theme.Material3.*` 来自 Material 库，
  不在本工程定义，拿它判悬空会误报）。
